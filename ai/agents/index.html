AI Agent 与自动化工作流：怎样协作而不失控

以嵌入式开发任务为例，理解规划、执行、测试、交接和人工门禁。

专题基础知识整理 · 与个人旧文章归档独立 · 例子以合成数据为准

以嵌入式开发任务为例，理解规划、执行、测试、交接和人工门禁。

1. Agent 与聊天模型有什么区别？

聊天模型负责根据上下文生成建议；工程 Agent 则多了状态、工具、工作目录、执行记录和反馈循环。一个能写代码的模型，不等于一个可以自主交付的系统。要检验它是否可靠，应检查真实文件差异、编译结果、测试日志与交付物，而不是只看它说“已完成”。

适合入门的闭环是：需求输入 → 计划和验收标准 → 修改可控范围内的代码 → 测试 → 人工确认。每一步明确输入和退出条件。

2. 多 Agent 协作应该怎么分工？

对于你使用的 Codex、其他编码 Agent 与独立审查 Agent，建议先使用共享任务卡而非复杂调度平台。规划角色只拆需求；编码角色只按任务卡修改；验证角色负责运行测试；质疑角色检查遗漏和证据。角色名称不重要，责任边界和交接契约才重要。

task_id: MOTOR-042
goal: 修复合成代码中的负占空比边界
scope: src/duty.c
acceptance:
  - 输入 -1 返回 0
  - 输入 500 返回 500
  - 输入 1200 返回 1000
evidence:
  - 编译命令与退出码
  - 单元测试实际输出
status: pending_review

如果测试没有运行，交接卡必须标注未验证，不得把另一模型的复述当作验收。

3. 如何避免 Agent 一直循环或互相甩锅？

每个任务设置明确的预算、失败次数上限、阻塞原因和人工升级规则。建议采用 待做 → 执行中 → 待验证 → 通过/失败/需人工处理 的状态流。一个 Agent 发现前一个 Agent 有遗漏时，生成带文件路径和复现条件的缺陷卡，再把任务返回编码阶段，而不是无止境互相对话。

没有真实的文件差异、测试日志或可审计的工作成果时，不能把任务标记为完成。

4. 权限、安全与成本边界

初期给 Agent 只读工具、合成示例仓库及有限目录写权限。涉及公司源代码、客户文件、机密测试数据时先确认模型与工具的授权范围。涉及实际电机启停、功率级、标定写入的动作，必须保留物理安全保护和明确的人为批准，不能由大模型文本直接触发。

记录总调用次数、Token/费用、人工返工时间和误报率；“Agent数量更多”不是效果更好的证明。

5. 5 分钟可以做什么？

拿一个合成 C 函数，先自己写出 3 条验收条件，再让 AI 提一个可能的边界问题。你负责亲自确认其中一条；这比安装整套 Agent 平台更适合作为起点。
