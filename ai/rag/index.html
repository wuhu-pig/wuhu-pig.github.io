工程 RAG 入门：从检索到带证据的回答

不是把 PDF 丢给模型，而是构建可溯源、可评测、尊重权限的知识系统。

专题基础知识整理 · 与个人旧文章归档独立 · 例子以合成数据为准

不是把 PDF 丢给模型，而是构建可溯源、可评测、尊重权限的知识系统。

1. RAG 实际在做什么？

RAG（检索增强生成）先从外部资料找相关证据，再让语言模型参考证据组织回答。它并不会自动保证答案正确；如果检索错了、文档版本旧了，模型也可能流畅地回答错误内容。

典型处理链路：文档准入/权限 → 解析 → 分块 → 索引 → 查询检索 → 重排 → 证据选择 → 生成与引用 → 评测。在工程知识库中，芯片料号、寄存器地址、文档版本和函数符号通常比通用语义相似性更重要。

2. 为什么需要混合检索与 Rerank？

关键词检索（例如 BM25）擅长匹配具体符号、寄存器名和错误码；Embedding 向量检索擅长匹配不同说法但语义相近的问题。混合检索可以同时获得两类候选。Rerank 再依据查询和候选片段的相关性重新排序，适当降低误召回。

例如用户问 “TLE987 ADC 采样触发在哪配置”，系统应优先匹配适当芯片型号及参考手册版本，不应仅因为另一款芯片的文段语言相似就给出答案。

3. 如何让回答能追溯？

索引时保留文档标识、版本、页码或章节、权限标签以及原文位置。回答时每个技术结论给出对应证据位置；没有证据时返回“目前资料无法确认”，再建议查阅具体文件。跨项目和跨权限的数据必须先在检索层过滤，不能只在提示词里要求模型保密。

要处理文档更新、撤销授权、删除原文后的索引失效，避免旧内容长期留在检索结果中。

4. 怎么判断 RAG 是否真的有效？

准备人工标注的小型问题集，并记录期望来源。分开评估检索命中率、引用是否支持结论、拒绝回答是否合理、总响应延迟。不要只靠同一个大模型对自己打分。先比较纯关键词基线，再比较混合检索和加入重排的结果，记录成功案例及失败案例。

当硬件比较有限时，本地先运行轻量 Embedding/检索，Rerank 选择小模型或按需调用，最终回答使用云端 LLM 是可行的架构之一；实际效率需用本机测试确认。

5. 一个可以今天完成的小实验

准备 3 篇公开技术文档和 5 个问题，手工标注“应该在哪一篇找到答案”，先用文本关键词找出候选。这样能先理解检索基线，再决定是否引入复杂框架。
