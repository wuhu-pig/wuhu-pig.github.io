本地大模型部署与选型：先做性能预算，再选工具

比较本地、云端和混合架构，从显存、延迟、模型质量与数据边界制定验证标准。

专题基础知识整理 · 与个人旧文章归档独立 · 例子以合成数据为准

比较本地、云端和混合架构，从显存、延迟、模型质量与数据边界制定验证标准。

1. 先明确本地运行哪一段工作

“本地部署 AI”可能指本地完整运行语言模型，也可能只在本地运行 Embedding、检索、Rerank，再调用云端模型生成答案。两种方案的硬件预算、质量上限和隐私边界不同。先写清楚目标是代码助手、RAG、离线问答还是自动化 Agent，再选择模型。

如果已有云端 LLM API，优先测试本地检索 + 线上回答的混合方案，通常更容易验证效果。

2. 显存和内存应该怎么估算？

模型参数量和权重量化位宽只是显存需求的一部分；还要考虑 KV Cache、上下文长度、并发数、推理框架工作区和操作系统占用。即使量化模型权重“能放进去”，也不代表长上下文或高并发下能稳定运行。

GPU 显存不足时可以尝试 CPU/GPU 分层卸载，但速度可能明显下降。低显存旧笔记本更适合小模型检索、数据预处理或云端模型前端，不宜将其作为大模型全本地高性能服务器的硬性目标。

3. Windows、WSL 与 Linux 怎么选？

Windows 本地实验不一定需要 Ubuntu 虚拟机；可以从已有的本地推理工具或 Windows 原生后端开始。部分推理框架和工具链在 WSL2 或 Linux 下有更成熟的 GPU 支持，但应根据所选框架、驱动和显卡支持情况确认，而不是先安装一整套虚拟机。

对于长期运行的服务，重点是可重复的安装脚本、资源监控、健康检查、备份与版本固定。

4. 至少记录哪些测试指标？

统一用同一组真实场景问题测试：首 Token 延迟（TTFT）、输出速度（Token/s）、端到端延迟、峰值显存/内存、异常退出次数、结果正确率与人工改写耗时。RAG 还需单独记录检索耗时和重排耗时。

只看模型排行榜或一次“看起来回答得不错”的演示不够；特别是低速设备，要测试多轮请求后是否积累资源问题。

5. 5分钟的第一步

写出你准备部署的具体任务、目标硬件显存、离线要求及期望响应时间，先选一个有答案标准的小问题集。之后再决定使用本地全推理还是混合方案。
