AI 如何真正提升嵌入式 C 的开发和调试效率

围绕代码审查、测试用例、FreeMASTER 波形和受控工具接口设计可靠闭环。

专题基础知识整理 · 与个人旧文章归档独立 · 例子以合成数据为准

围绕代码审查、测试用例、FreeMASTER 波形和受控工具接口设计可靠闭环。

1. 优先做低风险且能验证的任务

对于嵌入式工程师，AI 最值得先落地的场景通常是阅读代码差异、生成测试建议、解释日志、整理波形指标和维护需求追踪。先采用只读模式，只使用你获准共享的代码；不建议一开始让 AI 自动修改量产软件并直接提交。

一个有效的流程是：人工描述目标 → AI 提供建议 → 编译器/静态检查/测试工具给出客观证据 → 人工审查后合入。

2. C 代码审查必须关注什么？

除了命名格式，重点还包括有符号/无符号转换、溢出、移位、固定点缩放、数组边界、硬件寄存器副作用、中断共享状态和超时恢复。例如下面的合成示例：

#include <stdint.h>
uint16_t clamp_duty(int32_t duty) {
    if (duty > 1000) return 1000;
    return (uint16_t)duty;  // -1 会变成 65535
}

最小补充处理是先判断负值返回 0，再判断大于 1000 返回 1000，并覆盖 -1、0、500、1000、1200 等边界；最后必须实际编译运行，而不是只让 AI 写出预期。

3. FreeMASTER 与示波器数据如何交给 AI？

波形数据量大时，不要把整段原始数组塞进语言模型。优先由本地程序提取时间戳、采样率、通道单位、阶跃开始时间、上升时间、超调量、稳态误差、异常区间，再将聚合指标、必要的短窗口和截图交给 AI 解释。

FreeMASTER 的不同视图与接口能力可能不同；Oscilloscope 的屏幕操作不应被误认为 Recorder API 必然提供同一数据。先用只读连接确认真实的采样路径与通道映射，再讨论自动化。

4. 为什么必须隔离物理控制权？

代码审查 Agent 可以建议 PI 参数，但不应直接写 MCU 标定 RAM。实际调参需要范围限制、互锁条件、急停、离线仿真、安全审查以及现场操作者许可。对软件工程任务先证明节省了复核时间、降低遗漏，再考虑进一步自动化。

任何在真实硬件上的操作都应保留软件和硬件双重保护；模型不能成为唯一的安全决策者。

5. 入门练习与路线

今天先编译一个合成 C 函数，记录一个边界用例的实际输出，再请 AI 解释问题产生的整数转换规则。后续逐步扩展到 SVN Diff、Golden 测试集和波形 KPI。
